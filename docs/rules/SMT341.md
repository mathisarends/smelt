# SMT341 mixed-str-enum-values

StrEnum values are declared with auto() in one place and as explicit strings in another.

- **Category:** structure
- **Activation:** explicit — Enable by rule setting or --select.
- **Severity when active:** hint

## Why

StrEnum values should follow one canonical form across a project: either auto(), which derives the lowercased member name, or explicit strings. Mixing both, inside one class or between classes, hides which values are wire contracts and which are derived. This opt-in review considers production classes inheriting directly from enum.StrEnum (imported as StrEnum, an alias or enum.StrEnum). A class whose explicit strings all equal the lowercased member names could use either form; the form used by most such classes is the project style, auto() on a tie. A class is reported when it mixes auto() and explicit strings, or when it uses only the other form than the project style. Classes with custom values such as 'mouseMoved' must spell their strings and never decide or violate the project style, but auto() members inside them are reported. Member aliases, private names and tests are ignored.

## Bad

```python
class SignalingMessageType(StrEnum):
    DESCRIPTION = auto()
    READY = auto()

class ConnectionState(StrEnum):
    OPEN = "open"
    CLOSED = "closed"
```

## Good

```python
class SignalingMessageType(StrEnum):
    DESCRIPTION = auto()
    READY = auto()

class ConnectionState(StrEnum):
    OPEN = auto()
    CLOSED = auto()
```

## How to fix

Rewrite the reported class in the suggested style: replace explicit strings equal to the lowercased member name with auto(), or spell every auto() member as its lowercased name. Classes with custom values keep explicit strings. The finding names the project style and how many classes use each form. No automatic rewrite is performed. Enable rules: {mixed-str-enum-values: hint}, or select SMT341. Package overrides and reasoned inline suppressions are supported.
