# SMT108 package-import-fanout

One caller spreads a package API across several import paths.

- **Category:** dependencies
- **Activation:** policy — A package contract sets bundle_imports_at.
- **Severity when active:** hint

## Why

Repeated imports of neighboring implementation modules can indicate a missing package API. This is an opt-in design hint, not proof of poor architecture. Count distinct target modules per source file and contracted package, including its facade when mixed with implementation imports, not statements, symbols, or imports across the whole repository. Findings include missing static exports and a cycle witness for the proposed caller/facade edges. Known cycles block bundling advice. No-cycle-found covers only explicit runtime imports; dynamic imports and implicit package initialization remain unproven.

## Bad

```python
# caller.py
from app.users.application.get_user import GetUser
from app.users.application.update_user import UpdateUser
from app.users.application.delete_user import DeleteUser
```

## Good

```python
# caller.py, after deliberate facade exports are defined
from app.users.application import DeleteUser, GetUser, UpdateUser
```

## How to fix

Consider exporting the caller's supported API from the package facade. Use proposed_exports to review missing re-exports. A cycle_check of cycle blocks bundling: keep the imports or resolve dependency direction first. No automatic rewrite is performed. If these independent dependencies are intentional, retain them or adjust the advisory threshold. Declare public: ['.'] to enforce facade-only imports.
