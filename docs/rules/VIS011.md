# VIS011 visibility/deep-package-reexport

A package initializer re-exports a name through a deeper import path.

- **Category:** visibility
- **Activation:** explicit — Enable by rule setting or --select.
- **Severity when active:** warning
- **Automatic fix:** none; repair by hand
- **Guide:** Re-export through the immediate subpackage's initializer

## Why

When a package re-exports a name from a descendant module, every intervening package should expose it through its initializer. Each step in the export chain crosses one package boundary, so a subpackage can move its implementation without changing the parent initializer. The opt-in rule checks unconditional relative and absolute from-imports in production __init__.py files when the source module and the immediate subpackage initializer are in the project. Static __all__ identifies exports when present. Otherwise, imported bindings without a leading underscore count as public, including same-name aliases. Guarded or rebound bindings, star imports and dynamic export lists are outside its inference.

## Bad

```python
# app/__init__.py
from .runtime.hooks import ExecuteTool

__all__ = ["ExecuteTool"]
```

## Good

```python
# app/runtime/__init__.py
from .hooks import ExecuteTool

__all__ = ["ExecuteTool"]

# app/__init__.py
from .runtime import ExecuteTool

__all__ = ["ExecuteTool"]
```

## How to fix

Expose the imported names from the immediate subpackage, then import them from that package in the parent initializer. Apply the same pattern at each deeper package boundary. Preserve the parent's public aliases and review name collisions and import cycles before editing.
