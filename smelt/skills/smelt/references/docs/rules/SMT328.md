# SMT328 redundant-dishka-provider

A Dishka provider method only forwards typed dependencies to a constructor.

- **Category:** structure
- **Activation:** explicit — Enable by rule setting or --select.
- **Severity when active:** hint

## Why

Dishka can register constructors directly using provide(Implementation, provides=Interface). This opt-in review recognizes direct, undecorated Provider subclasses and synchronous @provide methods containing only one return of a class-shaped constructor call. Every typed dependency must be forwarded once, with matching keyword names or unchanged positional order. Stable direct Dishka import aliases are supported. Defaults, variadic signatures, extra decorators, mixins, async/generator/resource factories, transformations and unknown decorator options are excluded. Constructor annotations and dependency markers are not proven equivalent; the finding is a review candidate and never a graph validation or resource-ownership guarantee.

## Bad

```python
from dishka import Provider, Scope, provide

class AdminProvider(Provider):
    scope = Scope.REQUEST
    @provide
    def query(self, session: AsyncSession) -> AdminUserQuery:
        return SqlAdminUserQuery(session)
```

## Good

```python
from dishka import Provider, Scope, provide

class AdminProvider(Provider):
    scope = Scope.REQUEST
    query = provide(SqlAdminUserQuery, provides=AdminUserQuery)
```

## How to fix

Review registering the constructor directly. Verify its type hints and Dishka dependency/component markers supply the same inputs. Preserve class-level scope and explicit scope/cache/provides/override options. Keep factories with initialization logic or finalization. Suggested registrations use the canonical provide spelling; preserve the actual import alias when editing. No automatic rewrite is performed. Enable rules: {redundant-dishka-provider: hint}.
